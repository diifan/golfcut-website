# Incremental Tracer SEO for an existing app website

Read the app's AGENTS and website memory first. Resolve its real production Git repository, existing hosting project, canonical origin, Tracer capabilities, protected service worktree and publication authorization. Do not copy another sport's keywords or create a new site/project when the task is incremental.

Use GolfCut's [executor notes](../README.md) and deterministic scripts as the implementation reference. Keep operator config, pool, source cache, reservations, receipts, locks and timers app-specific. The controller contract lives in one config/state directory; do not fork it into a second scheduler config or edit its UI/API unless requested.

1. For the current GolfCut migration, use only the controller-delivered Semrush keyword pool with strict KD<30 and volume>100, traceable original exports and fetched evidence. Official video titles are not a substitute for a keyword pool. See [input contract](../INPUT-CONTRACT.md). Preserve already-published legacy video-reference pages, but block any further video-title batches. Establish real sources. When starting from zero, collect public sport-specific evidence immediately; an absent legacy pool is not a blocker. Prefer available public sources and existing exports. Browser sessions shared across apps must not be navigated. Do not issue quota-consuming queries when excluded by the user.
2. Cache and normalize evidence, append only new identities and preserve published/reserved states. Distinguish raw collected records, distinct candidates, fetch failures, evidence-qualified pages and published pages. A title from a source is a candidate, not verified search-volume data.
3. Render useful source-specific pages with original guidance and internal links; distinguish source facts from unobserved visual analysis. Do not invent athlete facts, imply endorsements, republish whole source descriptions or promise unsupported Tracer measurements. Enforce source/video/intent deduplication and report genuine shortages without padding.
4. Start from origin/main in a clean isolated worktree. Preserve the existing site, branding, APIs, legal content and live worker checkout. Use its existing Bun build, SEO validation, canonical and sitemap conventions. Test actual added interactions and small screens.
5. Stage the exact validated version to the existing production hosting project without promoting. Reconcile retries by batch and commit. At scheduled release, promote only a prebuilt validated version. Main changes require an isolated rebase/rebuild ahead of release; conflicts must remain explicit.
6. Verify live deployment identity, full batch sitemap coverage and page content before marking published. Reconcile Git with fast-forward only. Read mutable schedule/target settings each round, prepare next-day content early, retain idempotency locks and retry cooldowns, and update atomic receipts every 50–100 pages.

Report public examples, verified counts, commit/deployment and actual timer evidence. Do not call queued work or a build a completed publication. Do not send notifications unless separately authorized.
